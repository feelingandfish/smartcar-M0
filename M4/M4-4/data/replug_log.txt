================================================================================
 M4-4 破坏测试 ③：运行中拔线重插
================================================================================
测试日期 : 2026-11-15
测试环境 : Windows 11 + WSL Ubuntu-22.04 + USB-TTL(CH340,COM5,经 usbipd 接入 WSL)
           STM32F103C8T6 固件 M4-4.hex (32705 B)
协议版本 : CarLink v1.0（帧头 AA 55 / LEN / MSG_ID / 载荷 / CRC-16/MODBUS 小端）
测试工具 : linux/carlink（C 语言，termios + select + 断线重连）

--------------------------------------------------------------------------------
 【测试目的】
--------------------------------------------------------------------------------
在上位机持续运行期间物理断开并恢复串口链路，验证：
  1) 端口消失时上位机不崩溃、不退出，能持续重试
  2) 链路恢复后能自动重新打开串口，无需人工重启程序
  3) MCU 在断线期间是否继续正常运行（心跳计数是否连续）
  4) 断线期间丢失的帧数与心跳递增量是否吻合

--------------------------------------------------------------------------------
 【操作步骤】
--------------------------------------------------------------------------------
  1. WSL 内确认设备存在：ls -l /dev/ttyUSB0
  2. 启动上位机，持续运行 60 秒并同步记录 CSV：

         sudo ./carlink --port /dev/ttyUSB0 --speed 60 --duration 60 \
              --csv ../data/replug_test.csv

  3. 约第 15 秒，拔掉 USB-TTL 模块与电脑之间的 USB 线
     （上位机当场开始打印「打开 /dev/ttyUSB0 失败(No such file or directory)，
      200 ms 后重试」，程序不退出）
  4. 数秒后将 USB 线插回原 USB 口
  5. 在 PowerShell 中重新把设备接入 WSL：

         usbipd attach --wsl --busid 2-3

  6. 上位机在后台持续重试，约第 47 秒重新打开串口并自动恢复收帧，
     60 秒到点自动打印统计并退出

 注：拔插导致 USB 设备在 Windows 侧重新枚举，WSL 中设备节点随之消失，
     因此第 5 步必须重新 attach，这是 WSL + usbipd 环境的固有要求，
     与上位机程序的重连逻辑无关（程序的重连只负责反复尝试 open，
     不负责恢复 WSL 的 USB 映射）。

--------------------------------------------------------------------------------
 【CSV 断线区间定位】（data/replug_test.csv）
--------------------------------------------------------------------------------
    总行数       : 560（表头 1 行 + 数据 559 行）
    首帧         : t_ms=27    rpm=(0,0)   hb=45127  bad=8   tmo=11
    末帧         : t_ms=59977 rpm=(56,56) hb=46328  bad=33  tmo=40

    唯一一处时间跳变出现在第 300 行：

        前一行 t_ms = 14905
        后一行 t_ms = 47055
        跳变 = 32150 ms（约 32.15 秒）

    即：断线发生在第 14.905 秒，恢复发生在第 47.055 秒，
    断线时长 32.15 秒。该区间内 CSV 没有任何一行数据，
    说明上位机在断线期间确实一帧也没收到（不是收到坏帧，而是完全无数据）。


--------------------------------------------------------------------------------
 【数据自洽性验算】
--------------------------------------------------------------------------------
  ① 心跳递增量
        46328 - 45127 = 1201 帧
        （60 秒 × 20 Hz = 1200，多出的 1 帧为启动边界，符合预期）
     说明：MCU 在断线的 32 秒里一直在正常发帧，一帧都没有漏发。

  ② 接收端缺口
        理论应收 1200 帧，实收 559 帧，缺口 641 帧
        断线时长 × 帧率 = 32.15 s × 20 Hz ≈ 643 帧
        两者吻合，证明丢失的帧完全来自断线，而非解析错误。

  ③ 本端计数
        本端坏帧 = 0、本端超时 = 0、本端长度溢出 = 0
        说明上位机在重连后收到的数据是干净的，没有把断线瞬间的残片
        当成坏帧计入，恢复过程无污染。

  ④ MCU 侧计数
        bad 由 8 → 33（+25），tmo 由 11 → 40（+29）
        断线期间 USB-TTL 模块失电，PA9/PA10 处于悬空状态，
        MCU 收到的是随机电平噪声，可能凑出假帧头但 CRC 校验失败，
        因此 bad 与 tmo 在断线期间增长，属正常物理现象。
        ovf 全程为 0，环形缓冲未溢出。


--------------------------------------------------------------------------------
 【观察结论】
--------------------------------------------------------------------------------
1. 端口消失时上位机未崩溃、未退出：连续打印「200 ms 后重试」直至设备恢复，
   最终 60.01 秒按时完成并正常打印统计。

2. 串口重连次数 = 2（初始打开 1 次 + 断线后重连 1 次），
   证明自动重连逻辑生效，全程无需重启程序。

3. 断线 32.15 秒期间上位机一帧未收到（CSV 该区间完全空白），
   恢复后立即续上，末帧 hb=46328 与首帧 hb=45127 递增 1201，
   与 60 秒理论帧数一致，说明 MCU 端全程稳定运行。

4. 丢失 641 帧与断线时长 × 帧率（约 643 帧）吻合，
   丢失完全由链路中断导致，与协议解析正确性无关。

5. 恢复后接收数据无污染：本端坏帧 / 超时 / 长度溢出均为 0。

6. 断线期间 MCU 侧 bad +25、tmo +29，来源于 USB-TTL 失电后引脚悬空产生的
   随机噪声；ovf 始终为 0，环形缓冲（1024 B）未见溢出。

7. 上位机在断线期间仍按 20 Hz 尝试发送指令（共发 521 帧，
   理论 60 s × 20 = 1200，缺口即断线时段写入失败的次数），
   发送失败不阻塞主循环。
