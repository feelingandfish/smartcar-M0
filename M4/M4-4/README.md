## 2. 协议速览

### 2.1 帧格式

| 字段 | 长度 | 取值 | 说明 |
| :-- | :-- | :-- | :-- |
| 帧头 HEAD | 2 B | `0xAA 0x55` | 固定魔数，用于重同步 |
| 长度 LEN | 1 B | 0 ~ 64 | **载荷长度**（不含帧头/自身/ID/CRC） |
| 消息 ID | 1 B | `0x01`/`0x02`/`0x03` | 区分消息类型 |
| 载荷 PAYLOAD | LEN B | 见 2.2 | — |
| CRC16 | 2 B | — | CRC-16/MODBUS，**小端存放** |

**整帧长度 = 6 + LEN**（2 字节帧头 + 1 长度 + 1 ID + LEN 载荷 + 2 CRC）。

**字节序：小端（Little-Endian）**——所有 16 位字段的低字节在前。两端统一，STM32 本身是小端架构，按字节取用天然一致。

### 2.2 消息 ID 表

| ID | 方向 | 名称 | 载荷长度 | 载荷字段 | 频率 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| `0x01` | 上位机 → MCU | 速度指令 | 4 B | `left_rpm`(int16) + `right_rpm`(int16) | 20 Hz（`--rate` 可调） |
| `0x02` | MCU → 上位机 | 状态回报 | 14 B | 7 个 16 位字段，见下 | **50 ms** |
| `0x03` | 上位机 → MCU | 清计数 | 0 B | 无 | 按需（启动 `--clear` 或手工） |

**`0x02` 状态帧载荷（14 B，7 个 16 位字段，小端）**：

| 偏移 | 字段 | 类型 | 单位/含义 |
| :-- | :-- | :-- | :-- |
| 0 | `left_rpm` | int16 | 左轮转速，r/min，可为负 |
| 2 | `right_rpm` | int16 | 右轮转速，r/min，可为负 |
| 4 | `pitch` | int16 | 姿态角，**定点 0.01°/LSB**（×100） |
| 6 | `heartbeat` | uint16 | 心跳计数，每发一帧 +1，回绕 |
| 8 | `bad_frame_cnt` | uint16 | CRC 校验失败帧数 |
| 10 | `timeout_cnt` | uint16 | 帧内字节间隔超时次数 |
| 12 | `overflow_cnt` | uint16 | 接收环形缓冲溢出次数 |

### 2.3 CRC 参数

| 项目 | 值 |
| :-- | :-- |
| 算法 | CRC-16/MODBUS |
| 多项式 | `0xA001`（`0x8005` 的反射式写法） |
| 初值 | `0xFFFF` |
| 输入反射 | 是 |
| 输出反射 | 是 |
| 结果异或 | `0x0000` |
| **覆盖范围** | `frame[0] .. frame[3+LEN]`，即**帧头到载荷最后一个字节**，**不含 CRC 自身** |
| 存放 | 小端（低字节先发） |

### 2.4 示例帧（可由 `tools/frame_gen.py` 独立复算）

```
① 速度指令 60/60（与题面参考帧逐字节一致）
AA 55 04 01 3C 00 3C 00 EE 1D
│  │  │  │  └───┬───┘ └──┬──┘
│  │  │  │      │         └ CRC = 0x1DEE，小端存为 EE 1D
│  │  │  │      └ 载荷: left=0x003C=60, right=0x003C=60
│  │  │  └ MSG_ID = 0x01 速度指令
│  │  └ LEN = 4
└──┴ HEAD = 0xAA 0x55

② 速度指令 -30/45（验证 int16 补码）
AA 55 04 01 E2 FF 2D 00 E8 55
              └─┬─┘ └─┬─┘
  left = 0xFFE2 = -30（补码）  right = 0x002D = 45

③ 状态帧 (60, 59, 12.34°, hb=7, bad=0, tmo=0, ovf=0)
AA 55 0E 02 3C 00 3B 00 D2 04 07 00 00 00 00 00 00 00 16 DB
           │      │      │      │      │      │      │      └ CRC=0xDB16
           │      │      │      │      │      │      └ ovf   = 0
           │      │      │      │      │      └ tmo   = 0
           │      │      │      │      └ bad   = 0
           │      │      │      └ hb    = 7
           │      │      └ pitch = 0x04D2 = 1234 → 12.34°
           │      └ right = 0x003B = 59
           └ left  = 0x003C = 60

④ 状态帧 (60, 60, 0°, hb=123, bad=3, tmo=1, ovf=0)
AA 55 0E 02 3C 00 3C 00 00 00 7B 00 03 00 01 00 00 00 72 0D

⑤ 清计数
AA 55 00 03 71 ED
```

### 4.2 MCU 端行为

| 项 | 实现 |
| :-- | :-- |
| 收字节 | USART1 中断逐字节进 `ringbuf`（1024 B），主循环取空后喂状态机 |

## 6. 必须回答的问题

### 6.1 协议设计

**Q1：为什么不能只用和校验（checksum）？CRC 的检错能力在哪？**

和校验只是把各字节相加取低位，它有两个致命盲区：

1. **对字节顺序不敏感**：`3C 00` 与 `00 3C` 的和相同，交换两个字节和不变，查不出来。而串口错位、半截帧恰恰最容易产生这种"内容对、位置错"的情况。
2. **错误可以相互抵消**：一个字节 +1、另一个 −1，和仍然正确。

CRC 本质是**把整帧当一个大二进制数，用固定多项式做模 2 除法取余数**。每一位都参与运算，且带移位反馈，因此：

- 所有**单比特错误**必被检出；
- 一定长度内的所有**双比特错误**必被检出；
- 所有**奇数个比特错误**必被检出；
- 所有长度 ≤ 16 位的**突发错误**（连续一段比特被破坏，如干扰、丢字节）必被检出。

对本题最要命的两类故障——**丢字节导致的错位**和**插字节导致的长度错乱**——CRC 都能兜住，和校验兜不住。

**Q2：帧头 `0xAA 0x55` 如果出现在载荷里会怎样？怎么处理？**

会出现"假帧头"：接收方扫到载荷中间的 `AA 55`，会误以为新帧开始。

我们的处理不是"扫到 `AA 55` 就认"，而是**三步合一**：

1. **靠长度字段确定帧边界**：认下帧头后，按 LEN 收满 `6+LEN` 字节；
2. **靠 CRC 裁决真伪**：整帧算 CRC，对不上就判定这不是真帧；
3. **关键一步：CRC 失败后回退到该帧起始字节 +1，重新扫帧头**——不是整帧丢弃后从末尾继续，而是**退回一个字节**重新找。

这样处理的效果：

- 如果载荷里恰好有 `AA 55` 但整帧 CRC 正确，说明帧本身是好的，里面的 `AA 55` 只是数据，不影响；
- 如果因为假帧头切错位置，CRC 必然失败，回退 1 字节重扫，最多浪费一帧的时间就能找回真帧边界；
- **永远不会"脏一次就永久失步"**。

实测证据：注入 `AA AA 55 00 55`（含假帧头 `AA 55`）后，MCU 的 `bad` +1，随后立即恢复，14 秒内 281 帧一帧没丢。

**Q3：长度字段被干扰成很大的值，接收缓存会怎样？**

有两层保护，缓存不会被写爆：

1. **协议层上限**：LEN 合法范围为 0~64。收到 LEN > 64 直接判为非法帧，丢弃、计坏帧、回到找帧头状态，**不会按那个大数字去收数据**。
2. **缓冲层上限**：接收环形缓冲固定 1024 B，写满**覆盖最旧字节**。它是定长数组，不存在越界写——脏字节再多也只是覆盖，不会撑爆内存。

对应字段 `overflow_cnt` 会记录"写覆盖发生时缓冲已满"的次数，实测三次测试中**全程为 0**，说明 1024 B 对 115200 bps + 50 ms 状态帧的负载是充裕的。

### 6.2 MCU 端

**Q4：为什么用环形缓冲 + 状态机，而不是"读满一帧再解析"？**

"读满一帧再解析"隐含了一个假设：**每次读到的数据都从帧头开始、且刚好是一整帧**。这个假设在真实链路上必然被打破——拔插、干扰、半截帧、脏字节都会让它错位，而一旦错位，靠这个假设的解析器**永远对不上**（题面第 7 条明令禁止这种退化）。

环形缓冲 + 状态机的做法：

- **解耦速度**：中断里只做"把一个字节塞进缓冲"这一件事，几微秒完成，不阻塞、不丢字节；主循环有空再慢慢解析。中断频率（115200 下每字节约 87 μs）远高于解析耗时，两者不会互相拖累。
- **天然支持重同步**：状态机是**逐字节**推进的，任何时刻发现异常都能跳回 `WAIT_HEAD1`，从下一个字节重新找帧头。不存在"卡在某个半截帧里出不来"。
- **缓冲是定长的**：不会因为长度字段异常而动态申请内存，也就没有越界风险。

**Q5：如果上位机发得比处理得快，缓冲满了怎么办？丢最旧还是丢最新？**

**丢最旧（覆盖写）**。理由：

1. **时效性**：状态帧每 50 ms 一帧，内容是最新的转速和计数。过期的旧数据没有价值，保留最新的一段才有意义。
2. **重同步只需最近数据**：状态机找帧头只需要"最近若干字节"，不需要历史全量。丢最旧能保证缓冲里永远是"最近的 1024 字节"，重同步总能在最新数据上完成。
3. **丢最新的后果更糟**：如果保留旧数据、丢掉新到的字节，会造成"缓冲里是远古数据、串口还在源源不断地来新数据"，状态机永远在处理过期的字节流，恢复更慢。

同时 `overflow_cnt` 会累加，上位机能从状态帧里读到"发生过几次覆盖"，便于判断链路是否过载。实测三次破坏测试中 `ovf` 全程为 0。

**Q6：`bad_frame_cnt` 什么时候清零？**

**上电初始化为 0，运行期间只增不减；只有收到 `0x03` 清计数命令时才清零。**

理由：

1. **现场演示需要累计证据**：考官插完脏字节要读"到底坏了多少帧"。如果自动周期性清零，数字会被抹平，看不出效果。
2. **提供显式清零通道**：`0x03` 让操作者可以主动开新一轮计数，`carlink --clear` 就是在启动时先发这一帧，保证每次测试都从干净基线开始。
3. **上位机侧也保留独立计数**：PC 端自己也数 `本端坏帧计数`，与 MCU 的 `bad` 各自独立、互不覆盖，便于交叉核对（实测场景② 中 MCU bad=8 而本端坏帧=0，正说明两头各记各的账）。

### 6.3 健壮性

**Q7：场景① 里，坏帧计数应该是多少？为什么不会爆炸到无穷？**

**正确答案是接近 0**（实测 MCU `bad=0`、`tmo=0`）。

原因在于计数语义：`bad_frame_cnt` 统计的是 **"帧头匹配成功、但整帧 CRC 校验失败"** 的帧。而波特率错位时：

- 接收方按错误的位宽采样，得到的是完全无规律的字节流；
- 这串字节里**凑不出 `AA 55` 这个结构**（两个特定字节连续出现的概率极低）；
- 状态机一直停留在"等待帧头"状态，**根本没有机会进入 CRC 校验**，自然也不会给 `bad` 加 1。

所以计数不会无穷增长，反而保持不动。这恰恰是**正确行为**，而不是"计数坏了"。同理 `tmo` 也不涨：帧内超时只在"已经开始收一帧、但字节间隔超过 50 ms"时才触发，波特率错位根本起不了帧。

把波特率改回来后立刻恢复（实测 8 秒收 158 帧、心跳连续递增），证明两端都没被这次错误状态破坏。

**Q8：场景② 里，如果脏字节里恰好含帧头，会怎样？**

**会被误认为一帧的开始，但很快会被 CRC 否决，然后回退重扫，不会永久失步。**

具体过程：

1. 状态机扫到 `AA 55`，进入 `WAIT_LEN`，读长度；
2. 按长度收满字节，进入 CRC 校验；
3. CRC 对不上 → `bad_frame_cnt++` → **回退到该帧起始字节的下一个字节**，重新执行 `WAIT_HEAD1`；
4. 下一个字节如果是普通数据，直接跳过；如果是真帧头，正常解析。

最坏情况是连续几次假帧头，每次浪费一帧的时间并 +1 一次坏帧，但**不会卡死**。实测插入 `AA AA 55 00 55` 后 `bad` 精确 +1，随后的正常状态帧继续被完整解析，14 秒 281 帧无一丢失——这就是"脏一次不会永久失步"的直接证据。

> 这也是为什么"回退到起始+1"比"整帧丢弃后从末尾继续"更重要：后者会跳过一段可能含真帧头的数据，前者只退一个字节，保证不漏。

**Q9：场景③ 里，MCU 端知不知道上位机断开了？怎么知道？**

**知道，靠指令超时检测。**

机制：MCU 每收到一帧合法的 `0x01` 速度指令，就刷新一个"最后收令时刻"；主循环检查该时刻，**若连续 500 ms 没有新指令**（`CMD_TIMEOUT_MS 500`），判定上位机已离线，随即执行**安全停车**：

- 目标转速不再保持，而是每 10 ms 递减 5 r/min（`CMD_RAMP_STEP 5.0f`）**平滑**降到 0；
- 用斜坡而不是直接置零，是为了避免突然断电式的急停对电机和机械结构的冲击。

同时 MCU **自己不会停**：状态帧照常 50 ms 一帧发出，心跳照常递增。实测断线 32.15 秒期间，MCU 的心跳从 45127 涨到 46328（+1201），证明它全程在跑；而 `bad+25`、`tmo+29` 来自 USB-TTL 失电后 PA9/PA10 引脚悬空拾到的随机电平噪声，属于正常物理现象。恢复后指令重新到达，目标转速再按斜坡爬回 60，电机重新转起来。

## 7. Linux 串口四个坑的处理

| 坑 | 现象 | 本实现的处理 | 代码位置 |
| :-- | :-- | :-- | :-- |
| **① 终端模式吞字节** | 串口默认把 `0x0A` 当换行、`0x0D` 当回车、`0x11/0x13` 当流控，二进制数据被改写 | 调用 **`cfmakeraw()`**，并额外清 `IXON/IXOFF/IXANY`、`INLCR/ICRNL/IGNCR/ISTRIP`、`OPOST` | `serial.c` `serial_open()` |
| **② Ctrl-C 写进串口** | 默认 `ISIG` 开着，按 Ctrl-C 会把 `0x03` 字符发给 MCU，污染数据流 | `cfmakeraw()` 关闭 `ISIG`，同时装 **`SIGINT`/`SIGTERM` 处理函数**做优雅退出（打印统计、关 fd） | `serial.c` + `main.c` `signal()` |
| **③ 拔线后 read() 返回什么** | 设备消失时 `read()` 返回 `-1`（`errno = ENXIO/EIO`）或 `0` | **不空转**：`select` 超时 + 读失败后判定为设备错误，`usleep(200 ms)` 节流后重试，CPU 不被打满 | `main.c` 重连分支 |
| **④ 插回后是否要重开设备** | 拔插会让原 fd 失效 | **必须重开**：关闭旧 fd → 重新 `open` + 重新 `tcsetattr` → 继续。实测重连次数 = 2 | `main.c` 重连分支 |

补充两点本题特有的处理：

- 打开串口时用 `O_NONBLOCK`，配合 `select`，**任何时刻主循环都不会被 `read` 卡住**；
- 打开后执行 `tcflush(fd, TCIOFLUSH)`，**清掉上次会话残留在缓冲区里的半帧**，避免把旧数据当成本次的第一帧（这也是场景② 中"多收 1 帧"的来源）。

## 8. 参数逐个解释

### 8.1 命令行参数

| 参数 | 举例 | 含义 | 为什么可调 |
| :-- | :-- | :-- | :-- |
| `--port` | `/dev/ttyUSB0` | WSL 里 USB-TTL 的设备节点 | 换机器、换 USB 口后节点名会变 |
| `--baud` | `115200` | 串口速率，须与 MCU 的 USART1 配置一致 | **破坏测试①就是靠改它造错**；题面禁止写死 |
| `--speed` | `60` | 目标转速（r/min），下发到 MCU 的 `0x01` 帧里 | 验证不同转速下的响应；负数测反转 |
| `--rate` | `20` | 指令下发频率（Hz），即每 50 ms 发一帧 | 与状态帧 20 Hz 对称；设 0 则只收不发 |
| `--duration` | `30` | 运行多少秒后自动退出并打印统计 | 自动化测试必需；0 表示跑到 Ctrl-C |
| `--csv` | `../data/x.csv` | 每收到一帧状态就追加一行 | 交付要求"支持存 CSV"；用于事后画图 |
| `--raw` | `/tmp/raw.log` | 收到的原始字节按十六进制落盘 | 排错用：看线上到底来了什么字节 |
| `--clear` | — | 启动时先发 `0x03`，把 MCU 的 bad/tmo/ovf 清零 | 保证每次测试从同一基线开始 |
| `--quiet` | — | 不打印实时行，只写文件 | 长时间跑测试时减少刷屏 |
| `--selftest` | — | 跑 6 项内置用例后退出 | 不接硬件也能验证协议实现正确 |

### 8.2 协议字段与经济含义

| 名称 | 类型/长度 | 含义 | 为什么这样设计 |
| :-- | :-- | :-- | :-- |
| `0xAA 0x55` 帧头 | 2 B | 帧的起始标志 | 两个字节而不是一个，把"偶然撞上"的概率从 1/256 降到 1/65536；同时提供重同步锚点 |
| `LEN` | 1 B | 载荷长度（0~64） | 用载荷长度而非整帧长度，解析时直观；上限 64 保护缓存 |
| `MSG_ID` | 1 B | 消息类型 | 预留扩展空间：将来加 `0x04` 设 PID、`0x05` 读参数都不用改帧格式 |
| `left_rpm` / `right_rpm` | int16 | 左右轮转速，r/min | 有符号是因为要表达反转；16 位够表达 ±32767 r/min，远超实际 |
| `pitch` | int16 | 姿态角，0.01°/LSB | **定点**而非 float：串口上定点无精度歧义、跨平台一致、解析更简单 |
| `heartbeat` | uint16 | 心跳，每帧 +1 | **判断丢帧的核心**：连续性比计数总量更有用；uint16 回绕在 20 Hz 下约 54 分钟一圈，实测已验证回绕正常 |
| `bad_frame_cnt` | uint16 | CRC 失败帧数 | 现场演示"坏帧计数正确"的直接证据 |
| `timeout_cnt` | uint16 | 帧内超时次数 | 区分"内容坏了"（bad）与"根本没凑齐"（tmo） |
| `overflow_cnt` | uint16 | 缓冲溢出次数 | 判断链路是否过载、缓冲是否够大 |
| CRC16 | 2 B | 整帧校验值，小端 | 小端是因为 STM32 原生小端，直接按字节取用无需转换；两端约定一致即可 |

**`bad` 与 `tmo` 的区别**（现场最容易被追问）：

- `bad` = **凑齐了但校验不过**（帧头对、长度对、收到 CRC 段，但算出来不一样）
- `tmo` = **根本没凑齐**（已经开始收一帧，但 50 ms 内没有下一个字节，主动放弃）

## 9. 明确禁止项自查

| 题面禁止 | 本实现 |
| :-- | :-- |
| 禁止文本协议 | 全二进制，承载 0xAA/0x55 等非可打印字节 |
| 禁止假设"每帧开头对齐" | 状态机逐字节推进，CRC 失败回退起始+1 重扫 |
| 禁止 Linux 端用 Python | `linux/` 纯 C11；`tools/frame_gen.py` 只是文档验证工具，不参与运行 |
| 禁止不做 `cfmakeraw()` | `serial.c` 显式调用 `cfmakeraw(&tio)`，并额外清相关标志 |
| 禁止长度字段无上限保护 | LEN 上限 64，超限立即判非法；缓冲固定 1024 B 定长数组 |
| 禁止坏帧计数无法上报 | `bad_frame_cnt` 随每帧 `0x02` 上报，PC 端实时显示并写 CSV |
| 禁止两端字节序/CRC 范围不一致 | 两端共用同一份协议约定，`--selftest` 与 MCU 实测帧互验 |
| 禁止拔线后空转死循环 | 200 ms 节流重试，`select` 超时机制保证 CPU 不被占满 |

## 10. 现场交叉验证预案

考官可能会：把 MCU 端字节序改成反的，或把 CRC 覆盖范围改一格，然后看上位机反应。

**我们的预期表现：上位机报坏帧，而不是解析出"看起来合理但错"的数值。**

原因：CRC 覆盖**整帧（帧头到载荷末字节）**。任何一处字节被改动——包括字节序调换、覆盖范围变化、单个比特翻转——都会让整帧 CRC 对不上，直接被拒。不存在"校验过了但数值是错的"这种中间态。

这一点可以当场验证：

1. 把示例帧 `AA 55 04 01 3C 00 3C 00 EE 1D` 的 `3C 00` 改成 `00 3C`（交换字节序）；
2. 用 `tools/frame_gen.py parse` 解析，会得到 CRC 错误；
3. 用 `carlink --selftest` 的第 5 项（坏帧必须被拒）也能验证同一逻辑。

## 11. 已知限制与说明

1. **pitch 字段恒为 0**：当前硬件未接 MPU6050，姿态数据为空缺。协议字段已按 0.01° 定点预留，接入后直接填值即可，帧格式不变。
2. **单电机方案**：M4-3/M4-4 均为单电机（GA12-N20 带 AB 编码器），状态帧里的 `left_rpm` 与 `right_rpm` 填同一实测值，协议本身支持双轮独立。
3. **稳态转速在 52/56/61 之间跳**：编码器 1385 counts/rev，目标 60 r/min 对应每 10 ms 需 13.85 个脉冲（不可整除），故稳态必然在这几个值之间跳动，均值约 58。**这是低速量化天花板，不是控制故障**，PID 参数无需再调。
4. **`bad` 会随电机转动缓慢增长**：电机 PWM 开关噪声耦合到串口线所致（实测 200 帧增加 8 个），软件侧计数与重同步行为正确。物理缓解建议：串口三线远离电机线、确认共地。
5. **WSL 环境依赖 `usbipd`**：设备拔插后需在 PowerShell 执行 `usbipd attach --wsl --busid <id>` 才能重新出现在 `/dev/ttyUSB0`。这是 WSL 的 USB 映射机制，与上位机程序无关——程序的职责只是"反复尝试 open"，实测重连 2 次即证明该逻辑有效。
6. **参数名与题面示例不同**：题面示例写 `--dev` / `--send-rpm`，本实现用 `--port` / `--speed`，语义一致（见 4.1 节对照表）。
