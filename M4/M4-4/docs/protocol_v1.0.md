# M4-4 上下位机通信协议 v1.0

| 项 | 内容 |
|---|---|
| 协议名称 | CarLink |
| 版本 | **v1.0** |
| 适用链路 | STM32F103C8T6 ⟷ USB-TTL(CH340) ⟷ Linux 主机 |
| 物理层 | UART，115200 bps，8 数据位，无校验，1 停止位（**8N1**） |
| 传输方向 | 双向（上位机下发指令 / MCU 上报状态） |
| 文档状态 | 定稿，两端实现必须与本文件逐字段一致 |

> 本协议是**契约**：MCU 端与 Linux 端各自独立实现，只依赖本文件对齐。
> 任何一端擅自改动字节序、CRC 覆盖范围或字段顺序，另一端必须报**坏帧**，而不是"解析出一个看起来合理的值"。

---

## 1. 帧格式（总览）

| 偏移 | 字段 | 长度 | 取值 | 说明 |
|---|---:|---:|---|---|
| 0 | `HEAD0` | 1 B | `0xAA` | 帧头第 1 字节（魔数，用于重同步） |
| 1 | `HEAD1` | 1 B | `0x55` | 帧头第 2 字节 |
| 2 | `LEN` | 1 B | `0x00`~`0x40` | **载荷字节数**（不含帧头/长度/ID/CRC），上限 **64** |
| 3 | `MSG_ID` | 1 B | 见 §3 | 消息类型 |
| 4 | `PAYLOAD` | `LEN` B | — | 载荷，字段布局见 §4 |
| `4+LEN` | `CRC_L` | 1 B | — | CRC16 低字节（**小端存放**） |
| `5+LEN` | `CRC_H` | 1 B | — | CRC16 高字节 |

**整帧长度** = `6 + LEN`（最小 6 字节：空载荷帧）。

```
 0    1    2    3    4        4+LEN   5+LEN
┌────┬────┬────┬────┬────────┬───────┬───────┐
│ AA │ 55 │LEN │ ID │ PAYLOAD│ CRC_L │ CRC_H │
└────┴────┴────┴────┴────────┴───────┴───────┘
 └────────── CRC 覆盖范围 ──────────┘
        （偏移 0 到 3+LEN，不含 CRC 本身）
```

## 2. 字节序与数据类型

| 项 | 约定 |
|---|---|
| **全局字节序** | **小端（Little-Endian）**：多字节字段**低字节在前** |
| `int16` 负数表示 | **补码**（two's complement），例：-30 → `0xFFE2` → 字节 `E2 FF` |
| `uint16` | 无符号，范围 0~65535 |
| 角度 `pitch` | **定点**：`int16`，单位 **0.01°**（×100）。例：12.34° → 1234 → 字节 `D2 04` |
| 为什么用定点不用 `float` | ① 跨平台字节序/对齐无歧义；② 串口带宽省一半；③ 不会出现 NaN/精度漂移；④ 两端解析代码简单，便于独立复算 |
| 协议里**没有** `float` 字段 | 全部为整数，杜绝浮点表示差异 |

## 3. 消息 ID 表

| ID | 方向 | 名称 | 载荷长度 | 载荷字段 | 频率 |
|---|---|---|---|---|---|
| `0x01` | 上位机 → MCU | **速度指令** | 4 B | `left_rpm`, `right_rpm` | 按需（默认 20 Hz） |
| `0x02` | MCU → 上位机 | **状态回报** | 14 B | `left_rpm`, `right_rpm`, `pitch`, `heartbeat`, `bad_frame_cnt`, `timeout_cnt`, `overflow_cnt` | **固定 50 ms**（20 Hz） |
| `0x03` | 上位机 → MCU | **清计数** | 0 B | 无 | 按需（调试/演示用） |
| 其它 | — | 保留 | — | 收到后按"未知 ID"处理：计入坏帧，丢弃 | — |

> `0x02` 的 50 ms 由 **TIM 定时器中断**驱动，不使用 `delay`。

## 4. 载荷字段定义

### 4.1 `0x01` 速度指令（上位机 → MCU，4 B）

| 偏移 | 字段 | 类型 | 单位 | 说明 |
|---:|---|---|---|---|
| 0 | `left_rpm` | `int16` LE | r/min | 左轮目标转速，负数表示反转 |
| 2 | `right_rpm` | `int16` LE | r/min | 右轮目标转速，负数表示反转 |

> 本车为单电机方案，`right_rpm` 保留字段（当前固件忽略），保持协议完整以便双臂扩展。

### 4.2 `0x02` 状态回报（MCU → 上位机，14 B）

| 偏移 | 字段 | 类型 | 单位 | 说明 |
|---:|---|---|---|---|
| 0 | `left_rpm` | `int16` LE | r/min | 实测左轮转速 |
| 2 | `right_rpm` | `int16` LE | r/min | 实测右轮转速 |
| 4 | `pitch` | `int16` LE | 0.01° | 姿态角（MPU6050，本阶段未装则填 0） |
| 6 | `heartbeat` | `uint16` LE | — | 每发一帧 +1，溢出回绕。用于检测丢帧 |
| 8 | `bad_frame_cnt` | `uint16` LE | 次 | **CRC 校验失败**累计次数 |
| 10 | `timeout_cnt` | `uint16` LE | 次 | **帧内字节间隔超时**累计次数 |
| 12 | `overflow_cnt` | `uint16` LE | 次 | **长度字段非法**（`LEN > 64`）累计次数 |

### 4.3 `0x03` 清计数（上位机 → MCU，0 B）

收到后把 `bad_frame_cnt`、`timeout_cnt`、`overflow_cnt` **同时清零**，不改变 `heartbeat`。
回一帧 `0x02` 让上位机立刻看到归零结果。

## 5. CRC 参数（CRC-16/MODBUS）

| 参数 | 值 |
|---|---|
| 算法 | CRC-16/MODBUS |
| 多项式 | `0xA001`（即 0x8005 反射形式） |
| 初值 | `0xFFFF` |
| 输入反射 | **是**（RefIn = true） |
| 输出反射 | **是**（RefOut = true） |
| 结果异或 | `0x0000` |
| **覆盖范围** | **偏移 0（`HEAD0`）到偏移 `3+LEN`（载荷最后一字节）**，**不含 CRC 两字节本身** |
| 存放方式 | CRC 值按**小端**写入：先 `CRC_L`（低字节），后 `CRC_H`（高字节） |

**参考实现（可直接复算）**：

```c
uint16_t crc16_modbus(const uint8_t *p, uint16_t n)
{
    uint16_t crc = 0xFFFF;
    while (n--) {
        crc ^= *p++;
        for (int i = 0; i < 8; i++)
            crc = (crc & 1) ? ((crc >> 1) ^ 0xA001) : (crc >> 1);
    }
    return crc;
}
// 调用：crc = crc16_modbus(frame, 4 + len);
```

**独立验证方法**（考官可用）：

```bash
python tools/frame_gen.py crc "AA 55 04 01 3C 00 3C 00"
# 输出：CRC-16/MODBUS = 0x1DEE  (小端字节：EE 1D)
```

## 7. 接收端状态机（重同步是核心）

两端（MCU 与 Linux）使用**完全相同的状态机**，便于对称验证。

```
            ┌──────────────────────────────────────────────────┐
            │                                                  │
            ▼                                                  │
      ┌───────────┐  b==0xAA   ┌───────────┐  b==0x55  ┌──────┐ │
      │ WAIT_H1   │──────────►│ WAIT_H2   │──────────►│WAIT_L│ │
      └───────────┘           └───────────┘ 否则→H1   └──────┘ │
            ▲                       ▲                    │      │
            │                       │                    ▼      │
            │                  帧内超时>50ms         ┌────────┐ │
            │                       │                │WAIT_ID │ │
            │                       │                └────────┘ │
            │                       │                    │      │
            │                       │                    ▼      │
            │                       │              ┌───────────┐│
            │                       │              │WAIT_PAYLOAD││
            │                       │              └───────────┘│
            │                       │                    │      │
            │                       │                    ▼      │
            │                       │              ┌───────────┐│
            │                       │              │ WAIT_CRC  ││
            │                       │              └───────────┘│
            │                       │                    │      │
            │                       │                    ▼      │
            │                       │              ┌───────────┐│
            └───────────────────────┴──────────────│  校验CRC  ││
                   任何异常/校验失败都回到 WAIT_H1   └───────────┘│
                                                        │      │
                                                        └──────┘
                                                         成功→处理帧
```

**关键规则**：

| 规则 | 说明 |
|---|---|
| R1 | `WAIT_H1` 状态下收到非 `0xAA` 字节 → **原地丢弃**，继续等（这是"空转"，不计数） |
| R2 | `WAIT_H2` 状态下收到非 `0x55` → 若该字节是 `0xAA` 则留在 `WAIT_H2`（连续 AA 的情况），否则回 `WAIT_H1` |
| R3 | `WAIT_L` 收到 `LEN > 64` → `overflow_cnt++`，立即回 `WAIT_H1`（**不分配/不写入任何缓冲**） |
| R4 | 任何状态中，**距上一字节超过 50 ms** → `timeout_cnt++`，回 `WAIT_H1`，丢弃已收半帧 |
| R5 | CRC 校验失败 → `bad_frame_cnt++`，**回退到该帧起始字节的下一字节重新扫描帧头**，而不是丢弃这一整段 |
| R6 | 未知 `MSG_ID` → 计入 `bad_frame_cnt`，丢弃 |
| R7 | 载荷长度与 ID 声明的固定长度不符 → 计入 `bad_frame_cnt`，丢弃 |

**R5 为什么重要**：如果 CRC 失败后直接跳到"本帧末尾之后"，恰好会把紧跟其后、与本帧重叠的好帧一起跳过。从起始字节 +1 重新扫描，保证不漏帧。

**帧头出现在载荷里怎么办**（必答）：载荷内的 `AA 55` **不会**被误判为帧头，因为 `LEN` 字段已经明确告诉状态机"接下来 N 字节全部属于载荷"，状态机在 `WAIT_PAYLOAD` 阶段不做任何帧头匹配。只有 `WAIT_H1/WAIT_H2` 阶段才做帧头识别。这也是为什么帧格式必须有 `LEN` 字段。

## 8. 异常与边界处理约定

| 场景 | 约定 |
|---|---|
| **长度字段被干扰成很大值** | 上限 **64**；`LEN > 64` 直接判非法，`overflow_cnt++`，**绝不按该长度写入缓冲**。这是防止缓冲区被写爆的第一道门 |
| **帧内字节间隔超时** | **50 ms**（含发送方 20 Hz 的 50 ms 周期，留 1 个周期余量）。超时即丢弃半帧，回找帧头，`timeout_cnt++` |
| **接收缓冲上限** | 环形缓冲 1024 字节。写满时**覆盖最旧数据**（丢最旧、保留最新） |
| **丢最旧的理由** | 状态机能从任意错位重同步，丢掉旧半帧不会造成永久失步；而保留最新数据能更快拿到下一个完整好帧 |
| **`bad_frame_cnt` 语义** | **CRC 失败**次数（含未知 ID、长度不符）。**上电从 0 开始，不自动清零**，只有收到 `0x03` 才清零 |
| **`timeout_cnt` 语义** | 帧内字节间隔 > 50 ms 的次数 |
| **`overflow_cnt` 语义** | `LEN > 64` 的次数 |
| **计数回绕** | 三个计数均为 `uint16`，溢出回绕到 0，不饱和 |
| **上位机断线** | MCU 端**不需要**感知（继续按 50 ms 广播状态帧）。若需要在线检测，上位机侧用 `heartbeat` 停滞 > 200 ms 判为断线 |
| **非法短帧** | 整帧不足 `6 + LEN` 字节就收到下一帧头 → 当前帧按 CRC/长度不符丢弃 |

## 9. 设计问答（题面必答）

### Q1：为什么不能只用和校验（checksum），而必须用 CRC？

| 检错能力 | 累加和 | CRC-16 |
|---|---|---|
| 单比特错误 | ✅ 能检出 | ✅ 能检出 |
| **双比特错误** | ❌ 若两比特在同一字节、一增一减，和不变 | ✅ 检出 |
| **字节顺序颠倒**（`0x12 0x34` → `0x34 0x12`） | ❌ 纯加法，顺序无关，**完全检不出** | ✅ 检出 |
| **连续多字节错乱** | ❌ 概率性漏检 | ✅ 汉明距离远大于 2 |
| 突发错误（≤16 bit） | ❌ | ✅ 100% 检出 |
| 固定位置置位/清零 | ❌ 极易互相抵消 | ✅ |

本题考查的是**字节序不一致**这类"值都合法但顺序错了"的故障：累加和对此**完全无感**，CRC 必然报错。所以 CRC 不是"更保险一点"，而是本题唯一可行的选择。

### Q2：帧头 `0xAA 0x55` 出现在载荷里会怎样？

**不会误判**，原因见 §7：`LEN` 字段先于载荷被解析，状态机在 `WAIT_PAYLOAD` 阶段按长度整段吞掉字节，**不做帧头匹配**。

只有在**未进入帧（`WAIT_H1/WAIT_H2`）**或**CRC 失败后重同步**时，才逐字节寻找 `AA 55`。此时载荷里的 `AA 55` 只会让状态机"多试一次"，试到 CRC 失败后继续往下滑，**不会导致永久失步**（因为它的后续字节凑不出合法长度+合法 CRC）。

这也解释了为什么要把 `LEN` 放在 `MSG_ID` 之前、紧跟帧头——**先定长度再取内容**，是抵抗帧头污染的结构性保证。

### Q3：长度字段被干扰成很大的值，接收缓冲会怎样？

**不会爆**。三道防线：

1. **`LEN > 64` 直接拒绝**：不进入 `WAIT_PAYLOAD`，不写入任何缓冲，`overflow_cnt++`（§7 R3）
2. **编译期定长载荷缓冲**：`uint8_t payload[64]`，即使逻辑出错，物理上也写不出这个数组
3. **环形缓冲写满覆盖最旧**：即使外部灌入海量垃圾，缓冲也只是覆盖，不会越界

对比："按 `LEN` 动态申请/直接 `memcpy` 到不定长缓冲"的做法，一个 `0xFF` 就会写入 255 字节，溢出踩坏相邻变量——这正是题面禁止的。

## 10. 与实现的一致性要求

| 项 | 要求 |
|---|---|
| MCU 端 | `mcu/protocol.c` 的 `HEAD0/HEAD1/LEN/CRC` 常量必须与本文件一致 |
| Linux 端 | `linux/protocol.c` 必须与 `mcu/protocol.c` **逻辑对称**（可逐行对照） |
| 交叉验证 | 把一端字节序改成反的，另一端必须输出 `bad_frame_cnt++` 而**不是**解析出"看起来合理"的数值 |
| 示例帧 | 本文档全部示例帧均由 `tools/frame_gen.py` 生成，可用同一脚本独立复算 |
